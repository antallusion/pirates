# GRAVETIDE — Техническая архитектура

> Документ описывает целевую архитектуру MMO и то, как её уже воплощает рабочий прототип (Phase 1).
> Всё, что помечено **[сейчас]**, есть в коде этого репозитория. Всё, что помечено **[цель]**, — план масштабирования.
> Принцип, который не меняется ни на одном этапе: **сервер авторитетен**. Клиент присылает только намерения.

**[сейчас]** Все роли работают в одном Node.js-процессе (`server/src/main.ts`), но границы модулей совпадают с будущими сервисами:

| Будущий сервис | Модуль прототипа |
|---|---|
| Gateway / Session | `server/src/gateway.ts`, `net/gateway.ts` (WebSocket, версия, rate-limit, маршрутизация, reconnect), `net/link.ts` (внутренний канал к миру, `RemoteConnection`), `net/websocket.ts`, `Game.attach/onMessage/handle` |
| Auth | `server/src/auth.ts` (гостевые токены, в БД хранится только SHA-256) |
| Zone Server (физика, бой, абордаж, interest) | `Game.step`, `combat.ts`, `boarding.ts`, `abilities.ts`, `spatial.ts` |
| NPC Director / NPC simulation | `npc.ts` (LOD abstract/active, роли, маршруты), `nav.ts` (A*) |
| Economy Simulation | `economy.ts`, `ports.ts` |
| Weather / World Events | `weather.ts`, `Game.worldEvent` |
| Persistence | `server/src/persistence/db.ts` (`node:sqlite`, репозиторный API) |

Разрезать монолит на сервисы значит заменить прямые вызовы между модулями сообщениями по шине (NATS или Redis Streams). Игровые системы при этом не переписываются.

## 2. Авторитетность и анти-чит

### 2.1 Что присылает клиент **[сейчас]**

Только намерения (`shared/src/protocol.ts → ClientMsg`):

- `input { rudder ∈ [-1,1], sail ∈ {0..4}, seq }` — положение руля и ступень парусов. Позицию, скорость и курс клиент **не** присылает.
- `fire { side, dist }` — «дать бортовой залп на такую-то дистанцию». Сервер сам решает, заряжены ли пушки, хватает ли ядер и какой разброс. Дистанцию он зажимает в допустимый диапазон орудия.
- `board`, `ability`, `trade`, `shipyard`, `hire_crew`, `learn_talent`, `contract`, `pardon`, `insure`, `loot_take` — каждая просьба проверяется целиком: пришвартован ли корабль, хватает ли серебра, есть ли место в трюме, выполнены ли условия абордажа, пройден ли порог дерева талантов.

### 2.2 Что клиент **не может**

- Сообщить урон, золото, опыт, позицию, попадание. Урон считается только в `combat.ts → resolveHit/applyDamage`. Серебро и опыт меняются только в серверных системах, и каждое движение серебра пишется в `ledger`.
- Увидеть лишнее. Скрытые корабли (`Smoke Pots`, `Vanish into Fog`) не попадают в снапшот дальше 250 м. Острова приходят только чанками рядом с кораблём. На карте мира рисуются только открытые острова, а список открытий хранится на сервере. Абстрактные NPC (L0) клиенту не передаются вообще.
- Заспамить сервер. Лимит — 90 сообщений в секунду: лишние отбрасываются, при > 400 соединение закрывается. Сообщения > 64 КБ отклоняются на уровне фрейма. Неизвестные типы и невалидный JSON игнорируются.

Тесты `tests/game.test.ts` проверяют: зажим ввода, игнор мусорных сообщений, запрет второго залпа во время перезарядки, запрет торговли в море, запрет продажи контрабанды в законных портах.

### 2.3 **[цель]** Дополнительные меры

- Эвристики ботов: регулярность ввода, одинаковые маршруты, 24/7-сессии. Сигналы уходят в ревью, автоматических банов нет.
- Аномалии экономики: `ledger` агрегируется по часам, и система ловит всплески дохода, круговые сделки между аккаунтами и передачу ценностей новичкам.
- Сервер ничего не должен клиенту за «невидимое»: фильтрация видимости выполняется до сериализации, поэтому wallhack невозможен в принципе.
- Подпись билда клиента не нужна: доверия клиенту нет вообще.

## 3. Модель симуляции

### 3.1 Тик **[сейчас]**

- Фиксированный шаг **20 Гц** (`TICK_RATE`), аккумулятор времени, не больше 5 шагов за кадр таймера (защита от спирали смерти).
- Порядок шага (`Game.step`): раз в секунду — upkeep, лут, стриминг чанков и открытия; раз в 2 с — Director (квоты NPC); раз в 10 с — экономика (производство и потребление, погода); затем AI NPC → физика → столкновения кораблей → снаряды → абордаж → отложенные удары способностей → перезарядка и потопление → снапшоты (10 Гц) → автосейв (30 с).

### 3.2 Общий код клиента и сервера

`shared/src` — чистые детерминированные функции без побочных эффектов:

| Модуль | Назначение |
|---|---|
| `sim/sailing.ts` | Полярная диаграмма (прямое, косое, смешанное вооружение), ход, инерция, руль, течения |
| `sim/wind.ts` | Поле ветра: преобладающий ветер с медленным поворотом, региональные возмущения, порывы |
| `sim/shipstats.ts` | Итоговые характеристики: класс × модули верфи × пассивка × таланты × эффекты |
| `world/worldgen.ts` | Детерминированная генерация мира по seed: регионы, 580 островов, 24 порта, течения, nav-grid |
| `data/*` | Товары, корабли, орудия, боеприпасы, модули, капитаны, таланты, фракции |
| `protocol.ts` | Типы всех сообщений |

Клиент использует `sailing.ts` и `shipstats.ts` для экстраполяции своего корабля и для превью в верфи. Сервер использует их же для авторитетной физики. Расхождение модели невозможно по построению.

### 3.3 Предсказание и интерполяция **[сейчас]**

- **Чужие корабли** рисуются с задержкой 120 мс, с линейной интерполяцией между снапшотами (`lerpAngle` для курса). Если данные запаздывают, короткая экстраполяция длится до 250 мс.
- **Свой корабль**: последнее серверное состояние + `stepSailing` на прошедшее время (≤ 200 мс) с текущим вводом игрока, затем сглаживание (lerp 0.3). При расхождении > 40 м — жёсткая коррекция.
- **Ядра**: сервер шлёт одно событие `volley` с параметрами всех ядер (позиция, курс, дистанция, задержка). Клиент симулирует полёт сам, сервер присылает только `hit`. Это экономит трафик в 10–20 раз по сравнению с репликацией снарядов.

**[цель]** Полноценный rollback с буфером ввода по `seq` (поле `ack` в снапшоте уже есть) — когда задержки выше 150 мс станут массовыми.

## 4. Мир, разбиение и interest management

### 4.1 Масштаб

- Мир 96 × 96 км (`WORLD_SIZE`), сжатие ~6× относительно реальной навигации: быстрый корабль пересекает мир за 90–110 минут.
- 8 регионов (warped Voronoi), 580 островов, 24 порта (10 ключевых + 14 деревень), 6 морских течений, Стена Мальстрёма по краю мира.

### 4.2 Чанки **[сейчас]**

- Чанк 3 × 3 км (`CHUNK_SIZE`), сетка 32 × 32. Индекс «чанк → острова» строится при генерации.
- Клиенту стримятся острова из чанков в радиусе 2 от корабля (`CHUNK_STREAM_RADIUS`): при старте ~25 чанков, дальше по мере движения. Каждый остров отправляется ровно один раз.
- Навигационная сетка 400 м (`NAV_CELL`, 240 × 240) для A*-маршрутов NPC. Маршруты между портами кэшируются (`RouteCache`).

### 4.3 Interest management **[сейчас]**

- Динамические сущности лежат в `SpatialGrid` (ячейка 1 км) с инкрементальным обновлением.
- Для каждой сессии раз в 100 мс берутся корабли и лут в радиусе 2.2 км (`INTEREST_RADIUS`). Новые сущности получают `info` (статические данные: имя, класс, фракция), ушедшие — `gone`. Строки снапшота — позиционные массивы из 10 чисел.
- События (залпы, попадания, эффекты) рассылаются только тем, кто в радиусе события + 400 м.
- Приватное состояние капитана (`self`) отправляется, только если изменилось (сравнивается JSON-отпечаток).

### 4.4 **[сейчас]** Зоны и шардирование

Реализовано (`server/src/zones/zone.ts`, `shared/src/world/zones.ts`): зоны — группы регионов, процессы-зоны связаны сеткой каналов, призраки в полосе `INTEREST_RADIUS`, пересылка попаданий и засчитывания побед, handoff с переносом сессии через Gateway (`MOVE`), инвалидация общих записей. Ограничения текущей версии: зоны делят одну SQLite-базу (PostgreSQL — один процесс мира, у его write-behind кэша ещё нет межпроцессной согласованности); группы, сделки и дуэли не пересекают границу; вторичные последствия попадания по призраку (пожар, течи) остаются в зоне стрелявшего, до владельца доходит урон; раскладка статична.

Целевая схема:

- **Zone** — связная группа чанков, которую обслуживает один процесс. Стартовая раскладка — 16 зон (по 64 чанка), а горячие зоны (Black Coast, Gravewater) режутся мельче. Раскладка динамическая: балансировщик переносит чанки между процессами по нагрузке.
- **Border ghosts**: сущности в полосе 2.2 км у границы зоны реплицируются в соседнюю зону только для чтения. Интерес игрока собирается из основной зоны и её «призраков».
- **Handoff**: корабль, пересекающий границу, замораживается на 1 тик, его состояние (сущность + профиль) передаётся соседу, сессия перенаправляется Gateway. Бой через границу работает: снаряд принадлежит зоне стрелявшего, попадание по «призраку» пересылается владельцу цели.
- **Шард** — ~1 000–1 500 одновременных игроков на мир. Мегасервер (один мир для всех) — долгосрочная цель после стресс-тестов. До неё — несколько миров-серверов с одинаковым seed.

## 5. NPC: LOD-симуляция

| Уровень | Где | Частота | Что считается | Статус |
|---|---|---|---|---|
| **L0 abstract** | NPC Director | 20 Гц сейчас, 0.2 Гц в цели | позиция = точка на кэшированном маршруте по пройденной дистанции; груз, кошелёк, порт назначения; статистические встречи (пиратский рейд = груз не доходит, рождается слух) | [сейчас] |
| **L1 kinematic** | Zone | 5 Гц | движение по маршруту с упрощённым ветром, без боя; видны на дальнем радаре | [цель] |
| **L2 full** | Zone | 20 Гц | полная модель паруса, восприятие, лавировка, обход островов, бой, абордаж, капитуляция | [сейчас] |

- Переход L0 → L2 происходит, когда игрок ближе 3.2 км (`NPC_ACTIVE_RADIUS`): точка на маршруте становится физическим кораблём.
- Переход L2 → L0 — дальше 4 км в течение 8 с и не в бою: маршрут перестраивается от текущей точки до цели.
- Сейчас население — 44 торговца, 26 пиратов, ~24 патруля, 10 рыбаков, 2 корабля-призрака, охотники за головами по запросу. Director поддерживает квоты и подбрасывает пиратов к игрокам в неспокойных водах: «океан никогда не пуст».

Пример L0-записи (реальные поля `NpcBrain`): «fluyt *Salt Psalm* вышел из `blackwater` в `gravesend`, путь 14.2 км, пройдено 9.8 км, 118 сахара, кошелёк 640, роль merchant».

## 6. Экономика как физическая система

- У каждого порта есть `Market`: для каждого товара — запас, целевой запас, производство и потребление (единиц за `ECON_HOUR` = 15 мин). Цена = `base × clamp((target/stock)^0.6, 0.35, 3.2) × shock`, спред ±5.5%, налог законных портов 3%.
- Покупка и продажа идут по кривой: каждая единица сдвигает цену, поэтому круговая сделка в одном порту всегда убыточна (есть тест).
- NPC-торговцы выбирают маршрут по реальной марже (`bestRoute`), **физически** забирают товар из запаса одного порта и добавляют его в запас другого только по прибытии. Потопленный или ограбленный торговец означает, что товар не дошёл и в порту назначения возник дефицит.
- Мировые события (эпидемия, голод, осада, праздник, перепроизводство, стройка верфи) выставляют `shock`, который затухает.
- **[цель]** Economy Simulation выделяется в отдельный сервис, владеющий рынками. Zone-серверы работают с ним транзакционно (резерв → подтверждение), рынки кэшируются в Redis.

## 7. Персистентность

**[сейчас]** `node:sqlite` (WAL), схема:

| Таблица | Содержимое |
|---|---|
| `accounts` | id, имя (уникальное, case-insensitive), sha256 токена, даты |
| `captains` | JSON-профиль капитана (уровень, опыт, таланты, серебро, репутации, розыск, груз, корабль, контракты, открытые острова, кулдауны) + x, y, курс |
| `kv` | состояние мира: время, запасы всех рынков |
| `ledger` | журнал каждого движения серебра (покупка, продажа, ремонт, модули, корабли, штрафы, награды) |

- Сохранение: периодическое (30 с), при швартовке, отключении, гибели, остановке сервера. Всё пишется одной транзакцией.
- Профиль загружается через `sanitizeProfile`, который добавляет недостающие поля и зажимает значения, так что старые сейвы переживают обновления схемы.

**[цель]** PostgreSQL с нормализованными таблицами (`ships`, `cargo_items`, `crew_members`, `guilds`, `holdings`, `markets`, `ledger` с партиционированием по месяцам) и write-behind из Zone-процессов. Операции, где участвуют двое (обмен, абордаж игрока, гильдейский склад), идут через транзакции с идемпотентными ключами — это защита от дюпов.

## 8. Сессии и reconnect

- Токен хранится в `localStorage`. Повторный `hello` с токеном возвращает капитана.
- При обрыве корабль в море **остаётся в мире 30 с** (`LOGOUT_TIMER_SEC`) с убранными парусами и продолжает жить, если идёт бой (анти-combat-log). Переподключение в это окно возвращает управление тем же кораблём.
- Вход с другого устройства вытесняет старую сессию (код 4000, без автопереподключения).
- Клиент переподключается с экспоненциальной задержкой (0.5 → 8 с).

## 9. Сеть и трафик

**[сейчас]** JSON поверх собственного RFC 6455-сервера: текстовые фреймы, фрагментация, ping/pong, close, маскирование клиента обязательно, лимит 64 КБ.

Оценка трафика одного игрока в оживлённых водах (20 кораблей в радиусе): снапшот ≈ 20 × 60 B + 250 B ≈ 1.4 КБ × 10 Гц ≈ 14 КБ/с вниз. Для прототипа это приемлемо.

**[сейчас]** Снапшоты (горячий путь, 10 Гц) идут бинарными фреймами (`shared/src/codec.ts`, первый байт — версия формата); остальные сообщения — JSON. Снапшот с 20 кораблями занимает 529 Б против 1504 Б в JSON (в 2.8 раза меньше). Квантование:

| Поле | Кодирование |
|---|---|
| позиция | int32, шаг 0.1 м (**[цель]** int16 относительно центра чанка интереса) |
| курс | int16, шаг 1e-4 рад |
| скорость | uint16 (0.01 м/с); паруса, экипаж — uint8 (1/250); корпус — uint16 (1/10000) |
| флаги | uint16 |
| id | uint32 (**[цель]** varint, словарь сессии) |

**[цель]** Плюс delta-кодирование относительно подтверждённого снапшота, приоритеты (ближние 10 Гц, дальние 2–5 Гц) и агрегация событий. Ожидаемо 2–4 КБ/с на игрока.

## 10. Производительность

- Генерация мира ~80 мс. A* между портами: в среднем 0.55 мс, худший случай 33 мс (212 пар в пределах 40 км, 0 неудач); результат кэшируется.
- Шаг сервера при 100 NPC (≈ 5–10 активных рядом с игроком) занимает доли миллисекунды: абстрактные NPC стоят одну интерполяцию по полилинии.
- Столкновения и попадания ищутся только через `SpatialGrid`, проверка попадания — пересечение отрезка полёта ядра с эллипсом корпуса (`segmentHitsHull`).
- Клиент: Canvas 2D, острова рисуются path'ами с world-space паттернами текстур, свет — отдельный слой в половинном разрешении (`destination-out` + аддитивные ореолы).
- **[сейчас]** WebGL-слои моря и неба (`client/src/render/gl.ts`): шейдерная вода, биолюминесцентные следы, объёмный туман, молнии. 2D-холст поверх прозрачный. Спрайты кораблей и фракционных парусов собраны в атлас, у частиц есть LOD по нагрузке кадра.

## 11. Наблюдаемость и тесты

- `/health` отдаёт JSON: игроки, корабли, NPC всего и активных, снаряды, лут, мировое время.
- `npm test` запускает 23 теста `node:test`: модель паруса, статы и таланты, генерация мира, экономика, интеграция сервера (торговля, анти-чит, бой, абордаж, гибель, прогрессия, персистентность, LOD NPC) и настоящий WebSocket.
- `tools/e2e.mjs` — сквозной тест в Chromium через Playwright со скриншотами.
- **[цель]** Метрики Prometheus (длительность тика по фазам, размер снапшотов, число активных NPC, латентность БД), трассировка handoff, дашборды экономики из `ledger` (фоссеты и синки серебра).

## Нагрузочные измерения (Phase 6)

`tools/loadtest.ts` (боты по настоящему протоколу) и `tools/seed-bots.ts` (население, разошедшееся по региону). Один процесс мира, 4 ядра:

|---|---|---|---|---|---|
| Зона (`gravewater`) | 500 | 16 / 32 мс | 0 | 18 мс | 2.5 КБ/с |
| Зона (`gravewater`) | 1 000 | 36 / 68 мс | 0 | 46 мс | 3.4 КБ/с |

Бюджет тика — 50 мс (20 Гц). Толпа в одной точке — предел одного процесса; её снимают зоны и handoff (§4.4, Phase 7).

## Профилирование (Phase 10)

Каждый шаг сервера размечен по подсистемам (`Profiler` в `server/src/game/metrics.ts`): второй проход, корзины `shipSecond`/`sessionSecond`, директор, экономика и погода, ИИ NPC, физика, столкновения, снаряды, абордаж, PvE (боссы, экспедиции, Бездна), зоны и handoff, перезарядки, снапшоты, сохранение. `GET /health/profile` отдаёт по каждой подсистеме среднее, максимум и долю шага за последние 30 с; `tools/loadtest.ts` прикладывает этот профиль к отчёту.

Гавань, 300 ботов у одного причала (475 кораблей, худшая толпа):

| Подсистема | Среднее, мс | Доля |
|---|---|---|
| Снапшоты (interest + кодек) | 15.4 | 64% |
| Корзины раз в секунду | 5.7 | 22% |
| Столкновения | 1.3 | 5% |
| Физика | 1.0 | 4% |
| Снаряды, перезарядки, ИИ, PvE, прочее | < 0.4 каждая | < 2% каждая |

Тик в среднем 26 мс, p99 54 мс, без пропусков; RTT p95 24 мс.

**Вывод: переносить горячие системы на Rust/Go не нужно.** Физика и столкновения вместе занимают меньше 10% шага: даже десятикратное ускорение нативным кодом дало бы меньше 2 мс. Дорогие здесь снапшоты. Их цена растёт как «игроки × корабли рядом», то есть с плотностью толпы, а не со скоростью кода, поэтому её снимают уже сделанные архитектурные меры: 5 Гц в толпе, delta-кодек, зоны и handoff (§4.4). В обычной зоне при 500 ботах тик укладывается в 16 мс. Пересмотреть решение стоит, если при штатной нагрузке одна подсистема станет стабильно занимать больше 30% шага.
